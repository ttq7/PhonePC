# 此手机 (PhonePC)

一款模仿 **Windows 11 文件资源管理器** 的 Android 文件管理器，界面、图标、交互均对齐 Win11 桌面版「此电脑」——在手机上就叫「此手机」。

- **技术栈**：Kotlin + 原生 Android View（无 Compose / 无 Material 依赖，只用 AppCompat + RecyclerView）
- **图标来源**：**从本机 Windows 的 DLL 资源中提取的真实图标**（详见下文）
- **产物**：`dist\此手机-2.2-debug.apk`（约 5.9 MB）
- **已验证**：在无头 Android 15 模拟器上实机跑通，截图见 `preview/screens/`

## 2. 图标是怎么“复用 Windows”的

不是找的开源图标包，也不是画的，而是**直接问本机 Windows 要**：

1. **文件类型 / 特殊文件夹图标** —— 调 `IShellItemImageFactory::GetImage`（Explorer 自己渲染图标用的同一套 API），
   要 256×256 的原始图标。得到的 `file_jpg.png`、`folder_dl.png`、`drive.png` 等，
   就是你这台机器上资源管理器里显示的那张图。
   > 过程中踩了两个坑，脚本里都留了注释：先用 `SHGetFileInfo(SHGFI_ICONLOCATION)` 拿不到扩展名关联；
   > 换 `SHGetImageList(SHIL_JUMBO)` 返回的文件类型图标全是空白页；最后用 `IShellItemImageFactory` 才拿到真图。
   > 另外 `Bitmap.FromHbitmap` 会丢 alpha 通道，必须用 `GetDIBits` 手动读 32 位 BGRA 并反预乘。

2. **工具栏图标**（←、→、↑、刷新、剪切、复制、粘贴、重命名、删除、排序、查看…）——
   从系统字体 `C:\Windows\Fonts\SegoeIcons.ttf`（Segoe Fluent Icons）渲染字形，
   黑色 + alpha 输出，运行时按亮/暗主题 tint，和 Explorer 的做法一致。

3. `stage_res.ps1` 把 256px 原图缩成 mdpi/hdpi/xhdpi/xxhdpi/xxxhdpi 五套，共 **515 个 PNG** 打进 APK。

应用启动图标用的是 Win11「此电脑」的 PC 图标本身。

## 3. 功能

**界面（对齐 Win11 资源管理器）**

| 区域 | 内容 |
|---|---|
| 标题栏 | ☰ 菜单、**多标签页**（每个标签独立路径与历史，带图标和关闭按钮）、＋ 新建标签、▾ 视图菜单 |
| 地址栏 | ← → ↑ ⟳ 四个导航按钮、面包屑（此手机 › 内部存储 › …，可点击跳转）、**点击可切换为输入路径**、搜索框 |
| 命令栏 | 新建▾ 剪切 复制 粘贴 重命名 ｜ **按宽度自动折叠**，放不下的进 ⋯ 菜单 |
| 内容区 | 详细信息 / 列表 / 平铺 / 特大·大·中·小图标 共 7 种视图，图标视图加载**真实缩略图** |
| 状态栏 | 项目数 / 选中数量与合计大小，右侧两个视图快捷切换按钮 |
| 导航窗格 | 主页、图库、此手机（手机图标）、各存储卷、快捷查找、文件共享、回收站（带数量角标） |

选中任意项目后，命令栏自动切换成 Win11 的**选中态**：剪切 / 复制 / 重命名 / 共享 / 删除 / 全选 / 取消。

**文件操作（全部真实读写）**

- 浏览、进入、返回、前进、向上一级（每个标签独立的历史栈）
- 新建文件夹、新建文本文档（自动避让重名：`新建文件夹 (2)`）
- 重命名（冲突检测）、**批量重命名**（查找/替换 + `{name}` `{n}` `{ext}` 模板 + 实时预览，内部走临时名所以换名链不会互相覆盖）
- 复制 / 剪切 / 粘贴 / 删除，**删除默认进回收站**（可还原、可永久删除、可清空）
- **局域网共享**：内置 HTTP 服务器，电脑浏览器可浏览 / 下载 / 上传，支持 Range 请求
- 搜索：输入即过滤当前目录；回车则从当前目录**递归搜索**
- 排序：名称 / 修改日期 / 类型 / 大小，递增 / 递减（文件夹恒定置顶，且是 Windows 的**自然排序**）
- 属性对话框：名称、类型、路径、修改日期、可读可写、大小、文件夹项目数与递归体积，
  文件还会**单遍算出 MD5 与 SHA-256**（>256MB 跳过以避免卡顿）
- **缩略图**：图标视图里图片/视频显示真实缩略图（LruCache + 线程池，滚动不阻塞，回收视图不会错位）
- 打开文件（`FileProvider` + 系统关联）、共享（单/多选）
- **内置查看器**：图片（缩放 / 翻页 / 计数）、文本（查看 + 编辑 + 保存）、视频、音频，全在应用内完成；
  PDF / Office 这类仍需外部应用的格式会先交给系统，无人接收时落到内置信息页
- **新建各类文件**：文件夹、文本文档，以及 19 种常见类型 + 任意自定义扩展名
- **压缩包免解压浏览**：点开 zip / jar / apk 即进入归档视图，可像文件夹一样逐层进入、多选、
  「解压选中项」或「全部解压」（选中文件夹会连带解出其中全部内容）；条目名带 `..` 会被拒绝，防止路径穿越
- **APK 信息查看**：点开 apk 显示从包里读出的图标、应用名、包名、版本号/版本名、最低/目标系统、
  请求的全部权限，并可直接「安装」或「查看内容」（APK 本身就是 ZIP，复用同一套归档视图）
- 视图模式与排序方式自动记忆

**权限**：Android 11+ 走「所有文件访问权限」（`MANAGE_EXTERNAL_STORAGE`），并带引导弹窗；Android 8–10 走传统存储权限。

## 4. 编译

本机工具链：JDK 21、Gradle 8.9、Android SDK（android-36 / build-tools 36.0.0）。
`gradle.properties` 里有两个**因为工程位于 `E:\此电脑`（非 ASCII 路径）而必须加**的开关，已配置好：

```properties
android.overridePathCheck=true          # 让 AGP 放行非 ASCII 工程路径
kotlin.compiler.execution.strategy=in-process
# ↑ Gradle 在向 Kotlin 编译器 worker 序列化参数时会把中文转义成 \u6B64…，
#   导致 “source file not found”。改为在 Gradle 守护进程内编译即可绕开。
```

一键编译（沙箱内即可，依赖缓存和 Android 用户目录都放在工作区里）：

```powershell
powershell -File E:\此电脑\tools\build.ps1                 # 默认 assembleDebug
powershell -File E:\此电脑\tools\build.ps1 -Task clean
```

或手动：

```powershell
$env:GRADLE_USER_HOME='E:\此电脑\.gradle-home'
$env:ANDROID_HOME='C:\Users\asd32\AppData\Local\TyranoToolKit\android-sdk'
& 'C:\Users\asd32\AppData\Local\TyranoToolKit\gradle\gradle-8.9\bin\gradle.bat' `
  -p 'E:\此电脑\PhonePC' assembleDebug
```

**安装**：`adb install -r "E:\此电脑\dist\此手机-1.2-debug.apk"`

## 5. 已知限制

- **局域网共享无密码**：任何能连到该 Wi-Fi 的人都能读写共享目录，只在可信任网络里用，用完请停。
- **共享不会在后台存活**：服务器挂在应用进程上，退出应用即停止（没做前台服务）。
- **压缩包只读**：能浏览和解压，但不能像 WinRAR 那样直接在压缩包内增删改（写回 ZIP 需要重打包，未做）。
- **不支持加密压缩包 / 7z / rar**：只走 `java.util.zip`，ZIP 家族以外一律打不开。
- **归档内不能预览文件**：点压缩包里的文件只提示，需要先解压出来。
- **无 APK 逆向**：只看清单信息，不做 DEX / ARSC 编辑、签名、去校验。
- **内置查看器不覆盖 PDF / Office**：这些仍交给系统应用打开。
- **文本编辑器很基础**：没有语法高亮、没有查找替换、没有编码选择（固定 UTF-8）。
- **回收站不自动清理**：不会按时间/容量自动删除，需要手动清空。
- **撤销只有一次、7 秒**：撤销条只记住最近一次「移到回收站」，超时即消失（回收站里仍可手动还原）。
- **回收站只在主存储卷**：其他存储卷上的文件删除时会走「复制进回收站再删源」的慢路径。
- **进度按项目数而非字节数**：复制一个 2GB 的大文件时，进度条会长时间停在「1 / 1」，
  因为进度粒度是顶层项目数而不是字节。
- **大文本有上限**：超过 4MB 或含 NUL 字节的文件不以文本方式打开。
- **音视频用系统解码器**：能否播放取决于设备本身支持的编码格式。
- **无多选右键菜单**：长按弹的是单项操作菜单，多选模式下没有批量操作菜单（批量重命名除外）。
- **无双窗格**：横屏/平板上还不能左右分栏。
- 部分文件类型图标取决于**你这台机器上装的软件**（例如 `.html` 显示 Edge 图标、`.pdf` 显示 WPS 图标），
  这正是 Windows 上的真实表现。
- `Android/data`、`Android/obb` 在 Android 11+ 即使有全文件权限也读不到，现在会显示成「此文件夹为空」，
  没有给出明确的受限提示。
- 大文件复制没有百分比进度，只有不确定进度条 + 当前文件名。
- 大目录/大文件的递归体积统计有 20000 个条目的上限，避免卡死。

## 6. 更新记录

### v2.2（当前）
**快捷查找支持自然语言**：`我上午在百度下载的图片` 这类查询会被解析成结构化条件。

新增 `data/QueryParser.kt`，把中文查询拆成三类槽位，产出 `{时间窗口, 来源, 类型}`：

- **时间**：今天/昨天/前天/大前天、上午/下午/晚上/中午/凌晨/清晨/傍晚/深夜、
  本周/上周/本月/上个月、最近 N 天 / N 天内 / N 个月前
- **类型**：图片/照片/截图/视频/电影/音乐/录音/文档/表格/幻灯片/PDF/安装包/压缩包/代码/文本/电子书
- **来源**：复用 `QuickFind` 的应用别名表（QQ浏览器/微信/QQ/钉钉/夸克/UC/百度网盘/迅雷…）
- **填充词**：我/的/在/了/找/一下/那个/帮我… 会被丢掉，剩下的当作自由文本继续做模糊匹配

**为什么是解析器而不是模型**：`上午+百度+图片` 三个线索都在封闭词表里，抽取是确定性的。
而且它可解释 —— 解析结果可以做成可点掉的标签，模型理解错了你看得见。
**同一套 `Query` 结构正是端侧大模型要输出的东西**，所以模型以后插在前面，搜索侧不用改。

顺带把索引改成缓存元数据（名字/路径/扩展名/修改时间）。原来每次按键都要对全部文件调
`lastModified()`，五万个文件就是五万次系统调用 —— 结构化时间过滤会把这个开销放大到不可用。

**已知缺陷**：`qq` 现在被解析成来源「QQ」而不是「QQ浏览器」（QQ 那条记录里有个过于宽泛的 `qq` 关键字）。
结果仍然正确，但标签不准，需要收紧关键字表。

### v2.1.1
**撤回一句假话**。v2.1 我在应用提示文字和文档里写了「支持跳字模糊匹配，如 `xmbg` 找「项目报告」」——
这是编的，我没测过。算法是逐字符子序列匹配，`xmbg` 里没有任何一个字符出现在「项目报告」中，**永远不可能匹配**。
真正的拼音匹配需要内置拼音表，并未实现。已改成真实成立的例子（`rdme` 找 `readme`），文档也已更正。

同时修一个短查询误判：来源识别原本是双向包含（`it.contains(lower)`），
导致输入单个字母 `a` 就会命中「支付宝」「抖音」等别名、给无关目录加分。现在只做单向匹配（别名出现在输入中）。

### v2.1
**快捷查找**：模糊文件名 + 按来源找文件。

手机上找文件最难的不是拼不出文件名，而是你压根不记得叫什么，只记得「这是 QQ 浏览器下载的」。所以匹配走两条轴：

- **模糊跳字匹配**（fzf 式打分）：`rdme` 能匹配 `readme-说明.txt`，`dcmt` 能找到 `data/config.md`。
  打分区分「文件名开头命中 / 文件名中间命中 / 路径命中 / 跳字命中」，再加上「最近 7 天改过的文件加分」。
  注意：**只做字符跳字，不做拼音**，所以 `xmbg` 匹配不到「项目报告」——拼音需要内置拼音表，尚未实现。
- **来源别名表**：把应用俗称映射到它通常写入的目录。
  已收录 QQ浏览器 / 微信 / QQ / 钉钉 / 夸克 / UC浏览器 / 百度网盘 / 迅雷 / 支付宝 / 抖音 / 网易云音乐 / 蓝牙接收。
  输入 `qq` 时，**即使文件名里一个 q 都没有**，也能把 `/sdcard/QQBrowser/download/report-2026.pdf` 找出来，
  状态栏会写明「来源「QQ浏览器」」。

索引是启动时扫描一次内存快照（不落盘）—— 手机存储时刻在变，**一个漏掉你刚下载文件的陈旧索引，比等两秒扫描更糟**。
索引超过 10 分钟会在下次进入时重建，状态栏也有「重新扫描」。

实机验证（造了 QQ浏览器 / 微信 的真实目录结构和文件）：

| 输入 | 结果数 | 来源识别 | 命中 |
|---|---|---|---|
| `qq` | 1 | 「QQ浏览器」 | `report-2026.pdf`（文件名不含 q） |
| `rdme` | 20 | — | `readme-说明.txt` |
| `wechat` | 1 | 「微信」 | `wechat_file.docx` |
| `notes` | 4 | — | `meeting_notes_2026.txt` |
| `zzzznope` | 0 | — | 正确无结果 |

做法参考了现有项目：桌面端思路见 [android_everything（SQLite FTS5 全文索引）](https://github.com/luli395/android_everything)；
主流 Android 文件管理器（如 [Amaze](https://github.com/TeamAmaze/AmazeFileManager/issues/4330)）依赖系统 MediaScanner，
但那条路有「新建目录不被索引」的已知问题，所以这里改用自建内存索引。

## 7. 和 MT 管理器的定位差异

MT 管理器的官方功能表（[小米应用商店](https://app.mi.com/details?id=bin.mt.plus)、[百度百科](https://baike.baidu.com/item/MT%E7%AE%A1%E7%90%86%E5%99%A8/19053609)）核心是 **APK 逆向**：
DEX 编辑、ARSC 编辑、XML 编辑、APK 签名、APK 优化、APK 共存、去除签名校验、RES 资源混淆/反混淆、翻译模式，
以及双窗口、像 WinRAR 一样直接增删改 ZIP 内文件、支持正则的文本编辑器、Root 挂载读写。

**诚实结论：APK 逆向这个方向不是本项目要追的，短时间内也追不上。**
它真正的软肋是**交互与观感**——功能密度极高，但界面陈旧、触摸不友好、没有现代文件管理体验。
所以「超过」的路线不是堆功能，而是：

| 方向 | 现状 |
|---|---|
| Win11 资源管理器级界面与触摸体验 | 已有，且是 MT 没有的 |
| 真实缩略图 / 媒体优先浏览 | v1.3 已完成 |
| 多标签页 | v1.3 已完成 |
| 批量重命名、文件哈希 | v1.3 已完成 |
| ZIP 免解压浏览与选择性解压 | **v1.4 已完成** |
| APK 信息查看（包名/版本/权限/提取图标，只读不做逆向） | **v1.4 已完成** |
| 压缩包内增删改（写回 ZIP） | 待做，MT 的强项 |
| 双窗格（横屏/平板/折叠屏） | 待做，MT 有、Win11 也有 |
| 存储空间可视化分析、重复文件/大文件查找 | 待做，MT 较弱 |
| 内置文本编辑器 / 正则搜索替换 | 待做，MT 的强项 |
| FTP / HTTP 局域网共享 | 待做 |
| DEX / ARSC 编辑、去签名校验、Root 挂载读写 | **不在计划内** |
